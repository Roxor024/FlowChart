Send new consignment orders from Dataverse to SAP — automatically

When someone creates a consignment order, it’s created in SAP for them, the product’s translations are copied back, and the order is marked Synced. No copy-pasting between systems.

The outcome: how we’ll know it works
Every one of these will be tested before you use it.
An order with missing information never reaches SAP. You see the reason on the order.
“Synced” appears only when SAP has confirmed the order and every translation was saved.
Only languages in both systems get a translation. Skipped languages are listed with a reason.
Running it twice never creates a second SAP order or duplicate translations.
Example: SAP has English, German, French, Polish. Dataverse has English, German, French, Dutch. → 3 translations created, Polish skipped, order marked Synced.

How it will work

Five steps, all done by one automated workflow in Azure.

STEP 1
You create a consignment order
From a work order in Dataverse, like you do today.
STEP 2
We check nothing is missing
If something is missing, you see a clear message on the order.
STEP 3
We create it in SAP — and double-check
We confirm SAP really saved it before moving on.
STEP 4
We copy the product’s translations
Only for languages both systems use. See the rule
STEP 5
The order is marked “Synced”
Only when every step above has worked.
Our suggestion: keep it simple. One Azure Logic App (an automated workflow) runs all five steps. We’ll only add extra pieces if your answers show we need them.

If a language could match two options (e.g. “English” → US or UK), we don’t guess. We flag it for a person to check. If no languages match at all, the order shows “Needs checking” instead of Synced.

Mistakes it protects you from

These are built in, whatever your answers are.

No duplicate orders
If the flow runs twice, SAP still gets only one order.
No false “success”
SAP can say “OK” with warnings and still not save. We read the order back to be sure.
No endless loops
When we mark the order “Synced”, that change won’t start the flow again.
Problems are visible
If anything is unsure, the order says “Needs checking” instead of failing silently.

Question 1 of 5

How does SAP accept a new consignment order?
Why we ask: We have to send orders in exactly the format SAP expects, or SAP rejects them.
For your tech team: SAP interface contract — WSDL/XSD, BAPI/RFC name, IDoc type or OData service; one or many product lines?
Question 2 of 5
2
How can we be sure SAP really saved the order?
Why we ask: SAP can reply “OK” and still not save it. Checking stops lost or doubled orders.
For your tech team: Commit + read-back; can SAP store the Dataverse ID as an external reference (idempotency)?
Question 3 of 5
3
Where are the languages kept in Dataverse?
Why we ask: To match languages correctly (SAP calls German “D”, Dataverse calls it 1031).
For your tech team: Provisioned LCIDs or custom language table; SPRAS/LAISO ↔ Dataverse mapping; table + key column names
Question 4 of 5
4
Should the user wait for SAP, or just see a status?
Why we ask: SAP can be slow. Showing a status (Processing → Synced) avoids timeouts.
For your tech team: Sync vs async; trigger: Power Automate, plugin/webhook or Dataverse connector; required fields
Question 5 of 5
5
Where does your SAP system run?
Why we ask: This decides how Azure can reach SAP safely, and affects cost.
For your tech team: On-premises data gateway or VNet; Logic Apps Consumption vs Standard; identity for Dataverse

Workflow steps (one stateful Logic App)
  1. Trigger from Dataverse (status gate: only when Submitted)
  2. Validate required fields → on fail, write reason + Failed
  3. Idempotency check (existing SAP number / pending state)
  4. Map JSON → XML against the real SAP schema
  5. SAP create → check RETURN/warnings → commit → read back; uncertain → NeedsVerification
  6. Get product translations from SAP
  7. Get active Dataverse languages → intersect via one confirmed mapping
  8. Upsert translations (key = consignment + language); log omitted
  9. Write SAP number + Synced only if 5 and 8 fully succeeded
Sync vs async: waiting for SAP risks timeouts; a status field is safer.
SAP ok, Dataverse fails: store the SAP number first; retries resume at step 6.
Connectivity: on-prem SAP needs a gateway (Consumption) or VNet (Standard).
Alternative: add an Azure Function for mapping if rules get complex. Service Bus: not needed yet.
